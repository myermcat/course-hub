Work that serves every course page at once.

Keep the ticks when the browser forgets Everything marked done is held in one browser, so cleared site data or a second laptop opens a page with nothing ticked. Next

Where the ticks are now. Every tick box and every highlight is saved by the browser under a key for this site. It survives a reload and a restart. It is lost when site data is cleared, it never reaches a second device, and one browser knows nothing about the other.

The proposal. Google Firestore holds the state and Firebase Authentication handles the sign-in, arranged so the page keeps working with no account at all. The browser stays the default, and the page behaves signed out exactly as it does today. Signing in with Google copies what is in the browser up to Firestore, and from then on both are written together. A second device signed in to the same account opens with the same ticks.

Why the sign-in comes with it. A database with no sign-in has to allow writes from anyone who finds the address, and this repository is public, so the address is findable. With sign-in, a Firestore rule of the shape "a signed-in person may read and write only the documents under their own user id" means a stranger who signs in gets an empty private space of their own, and can neither see nor change hers.

What it costs to run. The Firebase configuration values are identifiers, so publishing them in a public repository is safe, and the security rule is what protects the data. The free tier covers a workload this size with room to spare.

How the data is shaped. One small document per course. A Firestore document stops at one megabyte, and the philosophy highlights are the part that grows, so a single document holding all four courses reaches that ceiling first.

The seam is already there. shared/tasks.js routes every read and every write through one object called store, so the change is that object plus a sign-in button.

Bring the problem pages into the shared stylesheet The ten pages under elg3125/pages/ still carry their own copy of the design system. Tidying

What each page carries. Its own colour tokens in all three theme states, its own type scale, its own table and its own toggle, around sixty lines repeated ten times. The only shared file any of them links today is shared/nav.css.

The change, per page. Delete the duplicated block, add <link rel="stylesheet" href="../../shared/hub.css"> above the nav stylesheet, and leave in the page's own <style> block only what belongs to that page: the ELG3125 accent and the column classes the problem table uses.

What to check afterwards. The figure and scan images, which the shared file says nothing about, and the back link at the top of each page. Do one page end to end in both themes before the other nine are touched.

What it saves. A change to a colour, a table or a toggle is one edit today. With these ten pages holding copies it is eleven, and the copies drift the first time one of the eleven is missed.

The philosophy guides stay as they are. They are published from a separate repository, so reaching this file would mean loading a stylesheet across origins, and that is a separate decision from tidying these ten.

Keep the three-way skill split current The split is decided and all three skills are written, and the shared one drifts every time a page or a component changes. Part done

What exists now. The original skill was written for reading philosophy. Separating what every hub shares from what belongs to one kind of course left three pieces.

  1. course-hub, the shared one. The design tokens, every component in shared/hub.css, the interaction rules, browser storage, the folder convention and the publishing steps. Both course skills point at it.
  2. course-readings, kept as it was. Its heart is narrating an argument for someone who will not read the source, which suits philosophy and suits nothing in an engineering course. It keeps the guide specification, the explanation standard and the optical character recognition pipeline for scans.
  3. course-problem-sets, new. The assignment table, the problem index, marking up source pages, worked solutions, and preparing for a weekly quiz.

Why one general skill was rejected. The explanation standard in the philosophy skill exists to stop summaries that teach nothing about an argument. A problem set has no argument to narrate, and folding the two together would either bury that standard or apply it where it does not belong. The parts genuinely shared are the interface and the prose, which is what course-hub holds.

What is left. The shared skill describes files that keep moving, and nothing checks it for drift. Its course table still gives the ELG3125 page at its old path, and its component list has to gain a row every time shared/hub.css gains a component. Both are a read-through after any change to the stylesheet or to where a page lives.

Get Oppenheim and Willsky, 2nd edition The book is in the course folder, and the problem index built from it checks out against Assignment 1. ELG3125Done

The copy in use. Second edition, ISBN 9780136511755, in the course folder. Problem 1.21 is on printed page 59, which matches the pages scanned for Assignment 1. Printed page plus 22 gives the page in the file.

uOttawa Omni returns six results for the author and title. One is the book that matters: Signals & systems, Oppenheim, Willsky and Nawab, 1997, on Reserve at Morisset plus other locations. A 1983 first edition with Young as third author is in the General Collection at QA 402 .O63 1983, and its problem numbering does not match what the assignments ask for.

There is no electronic copy through the library. The only results offering online access are a 1985 journal review of the book and two unrelated book chapters. A 2015 printing shows as not available locally.

Build a problem index from the textbook A script recorded which page each numbered problem starts on, so any later lookup costs one page. ELG3125Done

The book is never read into a conversation. A script walks the pages and writes a small table; the conversation only ever sees the handful of pages a given assignment needs, so the index cost almost nothing to build.

  1. Extract text page by page with PyMuPDF. If the source is photographs, run optical character recognition first with ocrmypdf, which adds a searchable text layer without changing how the pages look.
  2. Match problem markers at the start of a line, in the shape ^(\d+)\.(\d+)\., and record chapter, problem and page.
  3. Write Working files/problem-index.json as a map from problem number to page.
  4. Check the index against the five problem numbers already known from Assignment 1, which are on Oppenheim pages 59 to 61. If those come out right, the rest are trustworthy.

A whole textbook is far too large to read directly. The index makes the cost of a lookup independent of the size of the book.

Add the problem text to the assignments table Every row in the ELG3125 assignments table opens a page carrying the problem, its figure and the source page. ELG3125Done

What was built. Ten pages under elg3125/pages/, one per assignment except set 6 which runs to two, reached from the Questions column of the table on that hub.

Each problem appears twice, as typed text and as a picture, because neither alone is enough. Typed text renders the mathematics properly, can be searched, and costs almost nothing to revisit. Many problems refer to a figure, such as Figure P1.21 in the first assignment, and a figure has to be an image.

  • Typed statement. The problem written out in the page, with the mathematics set properly. This is what reads first.
  • The figure where one is referenced, cropped from the page and placed beside the statement.
  • The full source page inside a closed toggle, with the assigned parts ringed, for checking against the original.

Drawing the rings. PyMuPDF searches a page for the problem label, for example 1.21, which returns the rectangle holding it. Widening that rectangle to the column and adding page.add_rect_annot in the accent colour draws a ring around the problem. Rendering afterwards bakes the ring into the image. Only the assigned parts are ringed: for Assignment 1 that means 1.21 (c)(d)(e), 1.22 (b)(d)(e), 1.23 (b), 1.24 (c) and 1.25 (a)(c)(e), leaving the unassigned parts plain.

The marking was built and checked on the Assignment 1 scan first, because those three pages were downloaded while the rest of the book was still being sourced.

Extract transcripts for the lecture decks A plain text version of each deck makes searching a term across the whole course free. ELG3125Per lecture

Where they go. One text file per deck in Working files in the course folder on disk. The decks are Prof. Yao's, so they stay out of this repository and so do the transcripts.

How. PyMuPDF walks the pages of the deck and writes the text out. A deck takes seconds and needs no optical character recognition, because the slides carry a real text layer.

Where extracted text goes wrong. A slide whose content is an equation, a plot or a block diagram comes back as scattered symbols or as nothing at all. Rendered page images are kept for those slides and read directly, which is the expensive route and is used only where the text version fails.

What it buys. Finding which lecture covered a topic becomes a search across a folder of text files, with no deck opened and nothing large read.

It runs once per deck, so the item stays open all term and is cleared a lecture at a time.

How these pages work

One stylesheet serves every hub. The colours, the type, the cards, the tables and the task lists live in shared/hub.css, and each course page sets only its own accent colour: green for philosophy, blue for signals, amber for digital systems, purple for design. Changing how a card looks is one edit for all four.

Philosophy keeps its own repository. Its reading guides are published at an address that has already been shared and is written into four other files, so moving them would leave every one of those links pointing at nothing. The card above goes across to them instead.

Tick boxes are saved in this browser. Marking a task done on any of these pages writes to the browser you are using and survives a reload and a restart. The state does not travel to another computer, it is never sent anywhere, and clearing browsing data for the site removes it.

These pages were built with Claude from Brightspace, the course pages and the lecture decks. They are dependable on dates, rooms and weightings, all of which were read off a published source. Check anything that decides an answer against the course page itself, because a date can move after a page is written.
